# 子 agent 与自动化

本页讲让模型替你并行、定时、持续推进工作的四类机制：子 agent、工作流、自主目标、定时任务，以及配套的后台任务管理。

## 子 agent（spawn_agent）

模型可以派生子 agent：全新上下文、角色化工具白名单、完成后只把摘要回灌主会话。适合"交给它独立搞定一件事，别弄脏主对话"的场景。

- **内置两类**：`general`（全能，可读写）、`explore`（只读调查，可并行多个）
- **自定义**：在 `.step-code/agents/<名称>.md`（项目级）或 `~/.step-code/agents/<名称>.md`（用户级）写 agent 定义，项目级同名覆盖用户级
- **护栏**：单会话派生上限、嵌套深度上限、单 agent 轮数上限、并行并发上限，都可在 `[subagent]` 段配置（见[配置参考](./configuration.md)）

你不需要手动调用——描述任务时说明"派子 agent 并行调查这几个方向"即可，模型会自己决定。

### 并行执行

模型一轮可以返回多个工具调用，step-code 按**资源冲突**决定谁能并行：每个工具声明自己的访问面（无副作用 / 读某路径 / 写某路径 / 全局独占），互不冲突的并行跑、冲突的串行跑，结果始终按调用顺序回灌。所以多个 explore 子 agent、多次只读的 read/grep 会并行；写文件、`bash` 这类会串行。

并行子 agent 额外受 `[subagent].max_concurrent`（默认 4）的并发上限约束——超出的排队等空槽。授权确认始终串行进行（多个审批不会交错弹出）。这些都由模型自动处理，你不需要显式控制。

## 工作流（workflow）

比单个子 agent 更强的编排：模型用 `workflow` 工具声明式编排多个子 agent——`agent`（单步）、`parallel`（并行）、`fanout`（批量分发）、`synthesize`（汇总）。中间结果不占主会话上下文，只回最终报告。TUI 有步骤面板实时显示编排进度。

适合多阶段任务：比如"并行调研 5 个竞品，各自出摘要，最后汇总成对比报告"。

## 自主目标（goal）

给一个目标，让模型每轮自动续跑直到达成或阻塞：

```
你：/goal            # 查看目标状态面板
```

模型侧有 `create_goal` / `update_goal` / `set_goal_budget` / `get_goal` 工具。你只需用自然语言说"把 X 作为目标持续推进，预算 20 轮"，模型会建目标并自驱执行。`/goal pause` / `resume` / `cancel` 随时人工接管。

### 预算：轮次 + token

目标支持两种硬预算，可单设也可并用：

- **轮次预算**：最多自动续跑多少回合。
- **token 预算**：累计消耗多少 token（按计费口径累计，缓存命中不计）。

任一预算用到 ≥75% 时，模型会收到「预算将尽，收敛收尾」的提示自行收敛；任一预算超限则在回合边界标记为 blocked、停止自动续跑。预算是 opt-in 的——只有你明确给出硬限制时模型才设置，不会自行发明。blocked 后可 `/goal resume` 复活，但不放宽预算会立刻再次 blocked。

### 持久化

目标状态随会话一起保存。`--continue` / `--resume` 恢复会话时，原本 active 的目标会**降级为 paused**（防止重启后无人看管地自动烧 token），需要你 `/goal resume` 显式复活；paused / blocked 状态原样保留。分叉（`/fork`）出的会话不继承目标。

## 定时任务（cron）

到点把一段 prompt 注入会话自动执行：

```
你：每天早上 9 点检查一下这个仓库的 CI 状态
```

模型用 `cron_create` 建任务，`/loop`（别名 `/cron`）查看列表，可随时让模型删除。支持一次性（"30 分钟后提醒我"）和周期（cron 表达式）。

定时任务**按工作目录持久化**：每个任务一份 JSON 存在 `~/.step-code/cron/` 下对应 cwd 的分桶里，创建、删除、每次触发推进下次时间都立即落盘。所以进程重启、会话恢复后任务不丢，在这个目录下的任何会话都会接管它们。离线期间错过的触发，恢复后合并补投一次（注入文案里带漏跑次数）；创建超过 7 天的周期任务在恢复时清理。

## 后台任务

`bash` 工具支持 `run_in_background`：长命令（构建、测试、服务）转后台跑，主会话继续。配套 `task_list` / `task_output` / `task_stop` 管理，状态栏有 `bg:N` 徽章显示进行中的后台任务数。前台命令超时也会自动转后台（可在 `[background]` 段关掉）。

任务终态时主动注入完成通知，不用你轮询：

- **及时**：通知在回合边界就注入，模型下一个回合即可看到，不用等整个长任务循环结束。
- **精简**：通知本体压到一行（任务描述 + 终态 + 退出码），完整输出不内嵌——需要时模型用 `task_output` 自取。
- **不噪音**：你用 `task_stop` 亲手杀掉的任务不再发"已结束"通知。

一个反模式要避免：起了后台任务又立刻原地等它——那不如直接前台跑。后台任务的价值在于「先去做别的，完成时自动回来通知」。

## 使用建议

这几类机制的正当用途是**分担你的等待和协调成本**：并行的调查交给 explore 子 agent，多阶段的产出交给 workflow，需要持续推进的交给 goal，定时的交给 cron，耗时命令交后台。主会话只留需要你判断的部分。反过来，一句话能说清的小任务不要动用它们——机制本身有上下文和token成本。
